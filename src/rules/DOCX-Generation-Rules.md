# 云材料申报系统：Word 自动生成、格式对齐与填报规则规范

为了确保企业在申报 ISO 质量、环境、安全等各项体系认证时，导出的全套申请文件与合同具备 100% 的高合规性、高还原度和精美排版，系统在底层 Docx 解析与生成引擎中固化并执行以下三大核心规则：

---

## 一、 文档对齐要求 (Document Alignment Requirements)
系统需要根据企业申请的认证体系（单体系、双体系或多体系结合）以及企业填写的业务现状条件，动态精算并对齐所必需的 A 类申报材料包：

1. **基础必选件**：
   - 任何申报项目均强制包含 `BCZC-RC-01-A7  认证申请书.docx`、`BCZC-RC-02-A7  认证合同.docx` 及 `申请书附件7：产品或提供服务清单.docx`。
2. **地址不一致承诺对齐**：
   - 若企业的营业执照注册地址与实际经营/办公地址不一致，系统必须自动加入并生成 `承诺书.docx`（异地经营及真实性法定承诺书）。
3. **临时场所/信息技术对齐**：
   - 若企业申请范围包含临时场所，或涉及信息技术服务类（ITSMS、ISO 20000），系统必须自动追加生成 `申请书附件3：临时场所及服务项目清单.docx`。
4. **特定信息类安全防护对齐**：
   - 若申请体系中包含信息安全（ISMS/ISO 27001），必须自动打包保密声明（附件4）、信息安全客户基本信息（附件5）以及双向保密协议（BCZC-RC-02-A1）。
   - 若包含信息技术服务（ITSMS/ISO 20000），必须自动打包风险评价表（附件6）、保密声明（附件4）以及保密协议。
5. **特定产品/行业专属附件对齐**：
   - 能源管理体系（EnMS）自动对齐并打包 `能源管理体系信息表（附件8）`；
   - 人工智能管理体系（AIMS）自动对齐并打包 `人工智能管理体系基本信息（附件10）`；
   - 食品及餐饮类管理体系（FSMS/HACCP）自动对齐并打包 `食品类信息表（附件11）`；
   - 创新管理体系（InMS）自动对齐并打包 `InMS研发项目清单（附件12）`。
6. **B类线下自备资料清单自动打包**：
   - 系统在导出 A 类自动生成材料包的同时，必须根据所选体系动态筛选出客户需要线下自备的 B 类文件清单，并单独生成一份 `客户自备资料清单(B类).txt` 合理打包在 ZIP 压缩包内。

---

## 二、 格式对齐要求 (Format Alignment Requirements)
在生成 `.docx` 文件时，为了防止由于 Word 底层 XML 标记的不连续性导致内容破损、换行杂乱或公式错位，程序必须严格遵守并执行以下格式控制规则：

1. **表格表头多字符模糊清洗与匹配**：
   - 模板文件中的表格首列（Key）可能因人工编辑包含空格、全角/半角冒号（`：`、`:`）或全角/半角括号（`（`、`）`、`(`、`)`）。
   - 程序在扫描并对齐表格时，必须统一对首列文本进行正则表达式清洗剔除：
     ```python
     c0_clean = re.sub(r'[\s：:（）\(\)]', '', c0_txt)
     ```
     然后再进行精确的分支条件判定，确保绝不因为标点符号或空格不一致导致内容漏填或匹配失败。
2. **合同正文强制分页对齐**：
   - 为了确保《认证合同》的排版典雅、美观，合同第一页作为封面，合同正文部分（起自：“甲、乙双方依据《中华人民共和国民法典》…”）必须强制在 Page 2 首行开始。
   - 程序在遍历段落时，检测到该合同正文起始句后，必须在对应的段落属性元素（`<w:pPr>`）中动态注入分页符：
     ```xml
     <w:pageBreakBefore w:val="1"/>
     ```
     以此实现全自动、无感知的物理页面强制对齐。
3. **复选框选择器（□ 与 ☑）状态格式化**：
   - 程序在对表格中和段落中的复选框进行赋值时，必须保留原有描述文字，仅将状态字符进行高精度转换。
   - 选中时，将 `□目标选项` 替换为 `☑目标选项`，若未选中则保持 `□目标选项`，或在需要时将其他非对应复选框设为 `□`，确保排版不乱、不错位。
4. **段落级（w:p）重构文本替换（解决 w:t 拆分问题）**：
   - Word 在编辑或保存时，常将连续的一个中文词语或英文字段打碎拆分在多个不连续的 `<w:t>` 节点中，导致直接的 XML 字符串替换失效。
   - 程序在执行文本替换时，必须采用**段落级（w:p）全局重构文本替换机制**：
     - 首先在 `<w:p>` 级拼合所有子节点文本进行逻辑匹配。
     - 若发生匹配，则直接将替换后的新文本整体写入第一个 `<w:t>` 节点，并将其余子 `<w:t>` 节点的内容全部置为空字符串。
     - 这一策略在保留了段落原有的复杂样式（字体、字号、颜色、粗细）的前提下，完美解决了 Word 拆字导致的内容无法替换问题。

## 三、 数据填写规则 (Data Filling Rules)
系统必须严格依据国家认监委及博创众诚体系审核的要求，执行规范化的数据填写和逻辑校验规则：

1. **公司名称无死角全局兜底清洗**：
   - 模板中存在一些历史遗留测试公司名（如 `***公司` 或 `河北启恒电力科技有限公司`），分布在正文、页眉、页脚、声明或附录中。
   - 程序在处理完高精度表格及段落后，必须在写回文件前执行**全局无死角兜底清洗替换**：
     - 在所有的 `word/document.xml` 以及页眉页脚（`word/header*.xml`、`word/footer*.xml`）中，对所有包含 `***公司` 或 `河北启恒电力科技有限公司` 的文本执行全局强制替换，全面替换为用户填写的实际公司名称（`comp_name`）。
2. **合同签署栏 (Sign-Off Table) 精确分区更新**：
   - 在《认证合同》的双方盖章信息签署表中（通常左侧为“甲方”，右侧为“乙方”），程序在扫描时必须锁定该表。
   - 仅对左侧甲方（Column 0）所属单元格内的占位文字进行精准替换（如将名称替换为 `comp_name`，地址、法人、联系人、信用代码、银行账号、开户行等填充为甲方的实际数据）。
   - **绝对不触碰或改写右侧乙方（Column 1）的预设收款账户、收款开户行、乙方公司等核心条款及财务信息**，确保合同的合法性和安全性。
3. **关键人名与签署日期的填写规则**：
   - 合同和申请书中所有规定的“签字处”和“盖章处”（如：法定代表人签字、联系人签字、管理者代表签字、客户盖章等），系统在生成时**必须留空或仅保持纯文本人名**，由企业打印出纸质版后进行手写签字和物理盖章。
   - 合同及表单中的“签署日期”允许完全留空，以便企业在线下结合实际情况手写补充。
4. **多体系资料空缺填充与斜杠对齐**：
   - 如果是多体系认证（如 QMS/EMS/OHSMS 二合一或三合一），在主辅体系间存在一些不适用的空缺项目时，系统在保持原文内容的基础上，必须在这些空缺格内自动填充斜杠（`/`）予以占位并对齐，以便格式一致。
   - 如果是单体系认证，则对其他体系相关专属栏目写明“此项不适用”或画斜杠。
5. **逻辑时间演进与安全间距**：
   - 系统须根据企业是否有历史证书进行逻辑时间推算：
     - **若企业有历史证书**：根据其证书的发证日期，系统自动将管理体系首版发布实施日期（`impl_date`）推算到最早发证日期的 90 天前；首次审核日期（`audit_date`）和最终管评时间（`review_date`）也与之形成倒推。
     - **若企业为新建立体系**：首版发布实施日期（`impl_date`）自动推算至当前日期的 6 个月前，且体系建立运行时间（从发布实施到申请）必须**严格满 3 个月以上**（对于能源体系 EnMS 需满 6 个月以上），现场审核时间、管理评审时间必须分布在逻辑闭环中，防止时序倒置和弄虚作假。
